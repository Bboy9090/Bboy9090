# Portfolio Map and Polish Waves

This is an initial repository-level triage based on connected GitHub metadata, public entry points, and available build manifests. It is not a substitute for running every build and test suite. Scores and waves must change when machine evidence changes.

## Portfolio rules

- Keep one clear product owner per capability.
- Keep flagship products in separate repositories with versioned contracts.
- Do not merge projects merely because they share branding.
- Archive historical material instead of leaving obsolete completion claims in active documentation.
- Prefer a small proven vertical slice over a giant README describing the future.
- Public claims must match the highest evidence level actually achieved.

## Cross-portfolio execution waves

### Wave A — Truth and identity
- canonical names and one-line purposes
- product ownership map
- maturity labels
- archive obsolete completion claims
- clean public profile and repository descriptions

### Wave B — Build health
- locked installs
- format, lint, typecheck, unit, integration, smoke, and e2e lanes
- retained artifacts and checksums
- dependency and secret scans
- reproducible local commands

### Wave C — First-run delight
- authentic screenshots and demos
- sample data or projects
- onboarding and recovery from common setup errors
- accessible loading, empty, error, offline, and permission states

### Wave D — Signature experience
- one unforgettable capability per flagship
- measurable performance budgets
- consistent microcopy and interaction language
- stable saves, exports, migration, and rollback

### Wave E — Community and longevity
- contribution and security policies
- issue templates, labels, roadmaps, and changelogs
- release notes and supported-platform matrices
- feedback loops and fan-facing demonstrations
- maintenance ownership and archive policy
